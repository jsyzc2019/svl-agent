Addy Osmani：当 Agent 接手工作，如何保持批判性思考
作者
52nlp
2026年11月4号
Addy Osmani 在这篇 X 长文中讨论了一个每天都可能遇到的问题：任务交给 Agent 后，怎样保住自己的判断力？他从验证、审阅和需求表达讲起，给出了可以放进日常工作的小练习。
以下是全文翻译
以前，我们学到的批判性思考，是带着谦逊、好奇和适度的怀疑去接触新信息：听取不同观点，形成自己的看法。这一点依然成立。但现在，我的大量工作都通过 Agent 完成，日常工作里越来越少有事情会逼着我主动思考。对于那些已经全面拥抱 Agent 工作流的工程师和产品从业者——同时开着多个会话，也期待模型不断进步——我想先说清楚：我非常喜欢这些工具。写这篇文章，不是为了劝大家少用 Agent。
我的目标是：在一个什么都能轻易交给 Agent 的世界里，帮你保住批判性思考的能力。
过去，我们大部分的认知加工和审美判断，都发生在提出问题与得到答案之间。现在，这段间隔只剩几秒钟。Agent 工作流用得越多，这件事就越难，而且难法可能与大家预想的不同：模型越好，显而易见的错误就越少。许多，甚至大多数输出都会写得很好，基本正确，却不会让你觉得有必要再看一遍。
即使同时运行许多 Agent，你看这些输出时，仍然只有一双眼睛。
你得主动把批判性思考安排进每天的工作，因为默认情况下，没有什么会替你做这件事。
我们之所以很难自行纠偏，部分原因在于 Agent 工作流确实令人愉快。忙碌的一天里，快速得到顺眼、顺心、通常还正确的答案，当然很舒服。但也正因如此，我们很容易放松警惕。
卸载 依赖与投降
跟别人聊起这件事时，我会把它描述成一条连续的谱系。
最上面是
认知卸载（cognitive offloading）
：把任务交给 AI，但仍由自己掌控结果。我整天都在这么做，你也应该这样。中间是
依赖（deferral）
：工具的输出直接成了你的下一步输入，结果不再被当作一个有待检验的假设。最下面是
认知投降（cognitive surrender）
：AI 的输出悄悄成了你自己的看法，你也觉得没必要检查。
“认知投降”是沃顿商学院 Steven Shaw 和 Gideon Nave 提出的术语。它恰好描述了我看到的现象：信任，或者说懒惰，逐渐增加，人就沿着这条谱系往下滑。这种变化很少被察觉，因为每一步都很渐进，看起来也合理。上一份回答你仔细读过，于是下一份就略读；再下一份，只扫一眼骨架。等到有人问起其中某一行，你却解释不出来，甚至让 Agent 帮忙也说不清。
这就是认知投降，也是认知债务累积的方式。通常，只有当你试图调用对系统的心智模型，却发现它根本不存在时，问题才会暴露。Margaret-Anne Storey 写过，它在团队中的表现，是大家对同一套系统工作原理的共同理解不断被侵蚀。我也写过代码领域的对应问题：理解债务（comprehension debt），这个术语由 Jeremy Twei 提出。事情发生的当下，它完全不可见：代码库看起来干干净净，测试也都通过了。直到你要修改系统，才发现已经没人理解它。只看了一份战略文档或规格说明的目录，就签字通过，也是同样的问题。
说清楚一点，我不是在提不可能完成的要求。现代大型代码库的完整心智模型，不可能一直装在一个人的脑子里。Claude Code 团队公开说过，他们按需重建理解：需要了解某一部分时，就让 Claude 解释那一块，而不是把整个系统都记在脑中。正如我以前写过的，这类债务比大多数工程师想象中更容易偿还。只要能在需要时重建局部理解，你就不必始终保有完整模型。你只需要知道，自己缺少哪些理解。
风险低的地方，尽管完全委托出去。但如果一道问题的答案，连借助 Agent 你都解释不清，你就已经交出了掌控权。
这也不一定总是问题。就在最近，我录制一门课程，需要从三家评分相近的酒店里选一家作为录制地点。我没时间逐条看完所有评价，就把选择交给了 AI。结果不错，下次我还会这么做。但如果要决定怎样投资我们的钱、怎样给孩子的职业选择提建议，或者在工作中决定该做什么、哪些变更影响哪些用户、是否能安全上线，我就不会这样处理。出错代价小的事，可以交出去；后果需要别人承担的事，就得把推理留在自己手里。
我会问自己的问题
不知道自己到底怎么想时，我过去通常会回到一组最基本的问题：我怎么知道自己在解决正确的问题？怎么知道方法是对的？有没有证据支持我的结论？怎么知道已经做完了？多数时候，就是谁、什么、哪里、为什么、何时、如何。写出来看着幼稚得可笑，却会逼你考虑那些本来容易忽略的方面。如今，跳过这些，直接问 Agent 觉得你该怎么做，实在太容易了。下面是我现在会问自己的新版问题。
提问前，我有没有先形成一个假设？
让 Agent 做任何不简单的任务前，我都会先写下，哪怕只在脑子里想一下，自己觉得答案可能是什么。猜错没关系，看到新信息后随时可以改变想法。但读过一份写得很好的回答之后，再想象其他可能性就难了。如果完全没有方向，可以做一次 Thariq Shihipar 所说的“盲点检查”：把自己已知的东西交给模型，让它找出那些你甚至不知道自己不知道的部分。
我是在请它帮我思考，还是请它替我思考？
两种都可以，只要你知道自己正在做哪一种。
什么情况成立时，这个结论就会是错的？
然后去查。模型对自身把握程度的评估，远不如你实际能做的测试有价值，所以给它一个测试。
我有没有从另一个角度听过反方论证？
如果我在一个开放性问题上态度很坚决，就会让不止一个模型为相反观点辩护，再读它们的回答，形成自己的看法。这会多花一点时间，但最后我对问题的了解也会多得多。
当着那个将来要维护它的人的面，我敢为它下注吗？
代码如此，其他交付物也一样。我认为，这是能否对结果作出交代的标准。
哪些能力，我已经不再练习了？
也许是一些日常调试。我可以接受放下一部分，但希望这是有意识的选择。
把验证变成习惯
最近我写了很多关于验证的内容，因为我认为，瓶颈已经从写代码，转向确定自己做对了。给 Agent 提供验证工作的方法，无论是端到端测试、性质测试，还是真正操作应用，它就能修改、运行验证、读取输出、再次尝试，在你开始看之前完成这一轮。这就是 Boris Cherny 所说的“给 Claude 一个验证自己工作的办法”。我认为，这是获得好结果最关键的组成部分之一。你会更多地构建这些循环、审阅证据，而不是逐行阅读。
但验证本身也可能被你交出去。“有没有证据支持我的结论？”变成了“检查变绿了吗？”Agent 把创建测试变得很便宜，你会看到许多绿灯，但一个通过的测试，完全可能没发现已经坏掉的功能。如果测试和功能犯的是同一个错误，它就会通过。而绿灯只说明某一个性质成立，人却很容易以为它覆盖了一切。
检查变绿时，问问它证明了什么。然后再问，它没证明什么。
提前定义什么叫“验证通过”，因为等到事后，你会为任何结果找到合理的解释。
Agent 工作的完成标准，应该是看得见、摸得着的东西：通过的测试、截图、日志或轨迹。这样，判断工作是否完成就有了事实依据，而不是凭“看着像做完了”来解释，乃至放弃判断。收到 Agent 的完成通知后，在看总结之前，先看实际执行了什么命令，以及命令返回了什么。
Claude Code 还可以通过一个拥有全新上下文的子 Agent，对自己的工作做自我质疑，作为一次合理性检查。值得把它放进循环，让它每次都跑，而不是想起来才做。我在最后仍会问一句：“我遗漏了什么吗？”听起来很傻，但很多时候，我用前沿模型完成一个复杂功能，查看、审阅之后，再问“我遗漏了什么吗？”，它就又找出两三件事。所以我总会问。
当然，不是每次都需要做到这个程度；知道什么时候该深挖，本身就是一种能力。我们那篇介绍 Claude Code 团队如何做代码评审的文章里，有一条我很喜欢的经验：“如果说不清这些检查会漏掉什么，就请人认真评审，而不是快速点头通过。”
代码之外也一样。如果 Agent 帮你综合了五十次客户访谈，或者做了一份竞品分析，就抽几份源文档，确认总结准确。检查一个支撑你建议的关键数字，确认它算对了。
Agent 让搭建验证变得便宜。对你来说，难的是知道什么才算好的验证。
真正关注生成了什么
假设 Agent 交给你一个 600 行的 PR。你大致看了结构，没有逐行阅读。变量名看起来合理，测试也通过了，于是你批准合并。但中间某处，事务边界内的执行顺序悄悄变了，或者一个你没想过的边界情况，默认值被反转了。算起来，你确实审过，只是检查的都是自己早就知道会看到的东西。
写代码和审代码是两种能力，而审阅也会在某个时刻变成盖章放行。所以，读 diff 时，别因为代码是 AI 写的就区别对待。然后再跳出 diff，看看 Agent 作了哪些决定。在一个很长的会话里，它会替你作出许多小决定：默认值是什么，哪些不在范围内，两个要求冲突时，它重新解释了哪一个。
在一份“所有事情都很顺利”的总结里，你看不到这些，所以让它列出自己作的决定和假设。然后考考自己。随机挑几行，问：这行是怎么回事？那行呢？如果是文档，就先关掉，试着凭记忆写出主要论点。有些人有一个我很喜欢的长会话习惯：让 Claude 写一份变更报告，再在末尾给你出一份测验，规则是“只有全部答对，我才合并”。
要把即将交付的东西理解到足以为它辩护。因为总有一天，可能会有人问。
Agent 也可以帮你保护注意力。例如，我有个开源项目，会收到大量 PR。我会用 Agent 判断哪些东西提交进来了，哪些违背我们的指南，哪里可能需要我注意。我很少让 Agent 自己决定这些事，但它可以帮我缩小范围，让我把注意力放到该看的地方，真正思考这些修改是不是在用正确的方法解决正确的问题。
还有工作量的问题，你必须诚实面对。我把这称为“编排税”（orchestration tax）：Agent 生成的东西，与那些你愿意署上自己名字的东西之间，有一道差距。如果完成的工作堆积得比你看得还快，在解决这个问题之前，多开一个会话也无济于事。要么收紧检查，让更少的东西需要你亲自看，要么慢下来。
当产出的东西已经多到你无法为之负责时，你就不再是在审阅，而是在碰运气。
好的输入带来好的输出
人的心智模型依然参与其中，只是不再主要处于中间，而是移到了两端。你的精力投入在任务前端的描述与上下文，以及后端的输出审阅上。因此，好的输入对输出质量非常重要，我也把写好提示词视为一种批判性思考能力。
以前，如果你提出一个含糊的要求，会有人质疑它，你或许就会意识到：“等一下，我其实还没想清楚。”Agent 往往不会在这里拦住你。它会补上你没说的部分，交回一个看起来完成了的东西，哪怕背后的想法仍然模糊。我把这称为“意图债务”（intent debt）：那些并非你亲手写下的产物里，可能藏着隐含的目标、约束和理由。与其他债务不同，这一种没人能替你解决。意图必须来自你。
提示词反映了你对问题的理解。如果你说不清楚，可能它在你自己脑中也还不清楚。
寻求帮助之前，先用自己的话写一份需求简述。说明受众、哪些不在范围内，以及怎样才算完成。如果第二轮纠正还没让你得到想要的结果，就别再零碎调整了，重写提示词。
这件事也可以请 Agent 帮忙。我喜欢 Andy Clark 对“委托 AI 系统”和“与 AI 协作”的区分。后者会形成相互增强的良性循环：提示词让输出更清晰，输出让下一次提示词更清晰，也让你对问题的心智模型更清晰。如果哪里不清楚，就让 Agent 针对它不理解的部分采访你。会话结束时，如果你自己的心智模型也变得更清楚，那就是一个成功的信号。
同时，也要留意输入。每个 Agent 都很容易把上一个 Agent 的总结直接放进上下文，没过多久，第三个 Agent 就已经没读过原始文档了。
对于输出，你也需要自己的标准。我在很多不同的创作媒介中尝试过 AI，其中大部分作品从未公开，因为达不到我的标准。如今，所有东西都排版漂亮、语气自信，因此，外表精致已经不是有用的判断信号。
AI 也许让产出变快了，但如果我不愿意把作品归在自己名下，就不会把它拿出去。
某个东西达不到你的标准时，把原因写进共享配置、hook 或测试，避免它再次发生。审美和判断力就是这样积累起来的；记录为什么某个东西没能入选，本身也是一种好练习。
“但模型在这方面会比我更强”
如果你和我周围许多人一样，看好这个领域的未来，读到前面几节时，可能就已经在想：再过一两年，模型就能发现我能发现的问题了，那为什么还要费心保持这些能力？
在许多具体问题的发现上，你也许是对的。我自己也一直主张，把越来越多的检查交给 Agent。但我认为，这件事仍然重要，原因在于：最终交付的东西，总得有人负责。不管 AI 帮了多少忙，承担责任的仍然必须是人。
一个具体任务应该信任 Agent 到什么程度，本身就是判断的一部分。审阅工作有助于保持判断准确，因为模型犯错的方式一直在变。Anthropic 关于内部工程师和研究者的研究，把这个陷阱称为“监督悖论”：“监督 Claude 所需要的，恰恰是过度使用 AI 后可能退化的编程能力。”
下面这些是我最在意的问题，更好的模型也没法替我解决：你在做什么，为什么值得做，会影响谁，你愿意牺牲什么？这些问题都需要你回答。Agent 可以帮助你想清楚，我也希望它能帮忙，但归根结底，它们仍然是你的问题。
你可以把工作和大部分审计交出去，但不能把责任也交出去。
日常可以做的练习
不需要严格执行这里的所有做法。选那些适合自己工作流的就好。
每周，不用 Agent 写一点代码，或者亲手做一件一旦忘了怎么做就会很麻烦的真事。我把这称为“校准练习”，但这不是道德要求。每个月，写下自己已经不再做什么，再决定其中哪些是自己愿意放下的。我以前一篇文章里的问题，至今仍然成立：如果没有 AI，你会有多不知所措？
碰到超出自己理解的东西，就去学。如果写作时碰到一个从没见过的短语，我可以搜一句解释，然后塞进文中。但我更愿意做一点研究，把它真正弄懂，这样才知道它处在什么位置。
认真检查机器的工作，本身就是真正的工作。假装它不算工作，最后团队往往就不会去做。它不是免费的，所以把它作为一项工作排进计划，你才会真正完成。
不再练习的能力会消失，而且可能比你想象中更快。那些你不愿放弃的能力，就继续亲手用。
你可以带走的几件事
有意识地使用工具。
Agent 可以考你、采访你、向你展示证据，但前提是你作了这样的安排。那就安排起来。
诚实判断自己处在谱系的哪里。
如果连借助 Agent 都解释不了一个答案，你就已经交出了判断。
先有一个假设。
提问之前先想一个，哪怕不太靠谱。
绿灯只说明一件事。
它检查了什么？没检查什么？
寻找证据。
先读它运行了什么、返回了什么，再看总结。
阅读是为了知道它作了哪些决定。
它替你决定了什么？
打磨提示词。
你怎样描述要求，反映了你对问题理解了多少。
定一个标准，然后守住它。
不愿署上自己名字的东西，就别发出去。
亲手运用那些重要的能力，让自己始终参与其中。可以试一件事：提问之前，写下自己觉得会发生什么；Agent 完成之后，写下一件它没有检查的事。看看这是否改变了你阅读输出的方式。独立思考，提出更好的问题，为结果承担责任。
