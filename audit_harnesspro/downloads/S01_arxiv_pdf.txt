                                                                                            A BSTRACT

                                                     Harness development plays a crucial role in building capable AI agents. Re-
                                                     cent approaches improve harnesses through recursive self-improvement (RSI), but
                                                     their performance gains often come with higher execution costs. We introduce
                                                     H ARNESS P RO, a label-free method for evolving harnesses to improve task per-
                                                     formance while reducing execution cost. In this setting, candidate harnesses are
                                                     evaluated using LLM-generated tests without access to ground-truth solutions or
                                                     official tests. Specialized agents diagnose execution trajectories, plan updates with
                                                     different performance-cost priorities, and implement them as candidate harnesses.
                                                     Rather than returning a single harness, H ARNESS P RO uses normalized weighted
                                                     squared-distance selection to provide cost-focused (lite), balanced (medium), and
                                                     performance-focused (heavy) harnesses for different deployment budgets. Se-
                                                     lected harnesses enter the next iteration, where execution feedback guides further
                                                     updates. Our experiments cover Terminal-Bench 2, SWE-Bench Pro, and Pro-
                                                     gramBench, using GPT-5.5 with Codex and GLM-5.2 with Claude Code. Across
                                                     these benchmarks using GPT-5.5 with Codex, the heavy mode of H ARNESS P RO
                                                     achieves an average pass-rate gain of 2.0 percentage points and an average per-
                                                     task cost reduction of 26.1% relative to RHO. This advantage also holds when
                                                     using GLM-5.2 with Claude Code. Code is available at this link.


                                         1      I NTRODUCTION

                                         An agent harness is the software infrastructure that manages interactions between a large language
                                         model (LLM) and its environment (Grace et al., 2026). Recent work on recursive self-improvement
                                         (RSI) (Zhang et al., 2026) uses past execution trajectories to diagnose problems and guide harness
                                         updates that improve performance on future tasks (Suzgun et al., 2026; Lin et al., 2026; Pan et al.,
                                         2026a). However, these methods often pursue performance gains through more extensive explo-
                                         ration and stronger verification (Lin et al., 2026; Pan et al., 2026a). These efforts improve perfor-
                                         mance, but often at the cost of higher token consumption and increased latency. This trade-off is less
                                         appealing in practical deployment, where the execution cost and latency also matter. We therefore
                                         ask: Can recursive harness self-improvement deliver better performance at lower execution cost?
                                         Toward this goal, we introduce H ARNESS P RO, a label-free method for recursive harness self-
                                         improvement that uses both performance and cost metrics to guide harness updates and candidate
                                         selection. It orchestrates several specialized agents to turn execution feedback into successive har-
                                         ness updates. A trajectory analyzer examines repeated rollouts to identify failures and avoidable
                                         overhead. Guided by different performance-cost priorities, a planner turns these diagnoses into
                                         harness improvement plans, which an editor implements as executable harness candidates. A test-
                                         synthesis agent provides fixed tests for evaluating the candidates without access to ground-truth so-
                                         lutions or official tests. Candidates that underperform the initial harness or are Pareto-dominated are
                                         discarded. To accommodate different budgets, we then use normalized weighted squared-distance
                                         selection (Marler & Arora, 2004) to retain representative harnesses for cost-focused (lite), balanced

We evaluate H ARNESS P RO on Terminal-Bench 2 (The Terminal-Bench Team, 2025), SWE-Bench
Pro (Deng et al., 2026), and ProgramBench (Yang et al., 2026a), using GPT-5.5 with Codex and
GLM-5.2 with Claude Code. With both backbone models, H ARNESS P RO improves task perfor-
mance while reducing execution cost. For example, on Terminal-Bench 2 with GPT-5.5 and Codex,
the heavy mode of H ARNESS P RO outperforms RHO (Pan et al., 2026a) in pass rate by 4.5 percent-
age points while reducing mean cost per task by 33.9%. For more cost-sensitive deployments, the
medium mode delivers performance comparable to RHO at substantially lower execution cost.
An analysis of the evolved harnesses shows that H ARNESS P RO does not improve agents simply by
compressing context or increasing reasoning effort. The evolved harnesses dynamically allocate
reasoning effort and tool budgets based on task descriptions, while runtime hooks steer execution
from exploration toward convergence based on the assigned budgets. They also adopt tool-output
compression like RTK (Szymkowiak, 2026) and streamline instructions to reduce redundant prompt
content, while retaining necessary context and final verification. Together, these mechanisms curb
avoidable overhead while preserving the reasoning and verification needed for task success, thereby
advancing the performance-cost Pareto frontier. Our contributions are threefold:

       • We introduce H ARNESS P RO, a multi-agent framework that simultaneously optimizes per-
         formance and cost by analyzing execution trajectories and recursively improving harnesses.
       • We assess candidate artifacts with fixed LLM-generated tests rather than direct LLM judg-
         ments, improving failure detection without access to official tests.
       • Across three benchmarks, H ARNESS P RO improves performance while reducing cost and
         latency, yielding a series of harnesses with different performance-cost trade-offs.

2   R ELATED W ORK
Agent and harness optimization. Agent optimization has expanded from prompts and pre-
defined workflows to the executable harness surrounding a model. AFlow searches graphs of model-
invoking operators using execution feedback (Zhang et al., 2025). More recent systems directly
modify harness components: agentic harness engineering makes edits traceable (Lin et al., 2026),
HarnessFix diagnoses failures before applying repairs (Chen et al., 2026a), and HarnessX composes
harnesses from typed primitives using trajectory evidence (Chen et al., 2026b). RHO uses LLMs to
evaluate and compare execution trajectories without ground-truth labels, guiding harness evolution
toward higher task success (Pan et al., 2026a). In contrast, our method, H ARNESS P RO, optimizes
both task success rate and monetary cost. Rather than returning a single harness, it produces a set of
harnesses with different performance-cost trade-offs, organized into lite, medium, and heavy tiers.

Component optimization and inference-time budget allocation. Some methods focus on spe-
cific components, such as skills or memory (Pan et al., 2026b). SkillOpt optimizes skill docu-
ments (Yang et al., 2026b), while SkillMOO and FRAMES incorporate cost or regression constraints
into skill evolution (Gong et al., 2026a; Wang et al., 2026). Dynamic Cheatsheet and Reasoning-
Bank retain reusable strategies from past experience (Suzgun et al., 2026; Ouyang et al., 2026),
while Sleep-time Compute builds reusable memory by reasoning over context before a query ar-
rives (Lin et al., 2025). MemoryCPT jointly optimizes memory construction, retrieval, and summa-
rization (Lei et al., 2026). Other work addresses budget allocation at inference time: BATS learns
a budget-aware policy for allocating model tokens and external tool calls (Liu et al., 2025), while
COMPAS jointly selects models, prompts, and decoding settings according to task difficulty (Gong
et al., 2026b). H ARNESS P RO instead uses past trajectories to evolve the entire harness, including
instructions, skills, tools, hooks, and verification rules. Table 1 summarizes how H ARNESS P RO
differs from prior work.

Here, h0 is the initial harness. We seek the Pareto frontier and select three representative operating

ing these trade-offs poses two challenges. (1) A vast harness search space. A harness comprises
components such as instructions, tools, skills, hooks, and rules, all of which can be modified during
evolution. Their possible combinations create a vast, discrete search space that cannot be optimized
using gradients. (2) Balancing performance and cost. Additional reasoning, exploration, or ver-
ification can improve performance but also consumes more tokens, increasing cost. Conversely,
indiscriminately reducing these activities may hurt performance. Advancing the Pareto frontier thus
requires analyzing execution trajectories alongside task outcomes and token usage to distinguish
necessary computation from avoidable overhead and find the “sweet spot” that reduces cost without
compromising performance.

4.1       OVERVIEW

To keep trajectory collection and analysis manageable, we begin by selecting a training coreset
Dtrain . Following RHO (Pan et al., 2026a), we use the Determinantal Point Process (DPP) ker-
nel (Kulesza & Taskar, 2012) to balance task difficulty and diversity (Appendix A.1). Starting from
an executable harness h0 , we maintain a candidate set At of harnesses at epoch t, initialized as
A0 = {h0 }. In each epoch, H ARNESS P RO employs a multi-agent framework to analyze trajectories
of these candidate harnesses on the coreset Dtrain to identify task failures, unproductive exploration,
and redundant computation. The framework then plans and implements harness modifications to ad-
dress these issues, producing new executable candidate harnesses as described in Section 4.2.
We evolve harnesses in a label-free setting, without access to ground-truth solutions, official test
cases, or graders. Instead of using an LLM to assess and compare trajectories directly, as in
RHO (Pan et al., 2026a), we use it to generate tests from task descriptions and trajectories produced
by the initial harness. In each epoch, we evaluate candidate harnesses on the validation set using the
generated tests, measuring pass rate and execution cost. After discarding candidates that fall below
the performance floor or are Pareto-dominated, we use normalized weighted squared-distance selec-
tion to retain representatives for cost-focused (lite), balanced (medium), and performance-focused
(heavy) modes. The selected harnesses form the candidate set for the next epoch. This process re-
peats until the epoch limit is reached, after which we fix the harnesses and evaluate them on the test
set. Algorithm 1 summarizes the full procedure.

5.1   E XPERIMENTAL S ETUP

Data and implementation. We evaluate H ARNESS P RO on Terminal-Bench 2 (The Terminal-
Bench Team, 2025), SWE-Bench Pro (Deng et al., 2026), and ProgramBench (Yang et al., 2026a),
covering terminal tasks, repository-level issue resolution, and program reconstruction. Following
the dataset splitting protocol of RHO (Pan et al., 2026a), we hold out 59, 100, and 100 tasks, re-
spectively, for testing. From the remaining tasks in each benchmark, we select a 10-task training set
Dtrain using the DPP-based coreset selection method (Kulesza & Taskar, 2012) described in Sec-
tion 4.1. The remaining tasks form the validation set. We pair GPT-5.5 with Codex 0.147.0 and
GLM-5.2 with Claude Code 2.1.231. Each candidate harness produces G = 3 rollouts per
training task in each epoch. Evolution runs for three epochs on Terminal-Bench 2 and SWE-Bench
Pro, and four on ProgramBench, retaining up to three harnesses after each epoch. All methods use
the same data splits and grading settings. Further implementation details are in Appendix A.

Baselines. We compare H ARNESS P RO against several strong harness optimization methods. The
original Codex or Claude Code harness is Vanilla, the starting point for optimization. Dynamic
Cheatsheet (Suzgun et al., 2026) maintains reusable strategies and code snippets, Reasoning-
Bank (Ouyang et al., 2026) retrieves strategies distilled from past trajectories, and Sleep-time Com-
pute (Lin et al., 2025) prepares reusable memory before new tasks. RHO (Pan et al., 2026a) revises
harness components through trajectory analysis and selects candidates using LLM self-preference.
To separate the effects of cost-aware and recursive optimization, we include two RHO variants. Bal-
ance changes only RHO’s optimization instruction, asking for better task performance at lower cost.
RHO+Iteration runs Balance for the same number of epochs as H ARNESS P RO. Each subsequent
epoch starts from the harness selected in the preceding epoch by the best-of-N procedure of RHO.

Evaluation metrics. On Terminal-Bench 2 and SWE-Bench Pro, a task passes only if all its of-
ficial tests pass. For ProgramBench, we follow its official evaluation protocol (Yang et al., 2026a)
and report pass rate as the macro-average of the fraction of test cases passed for each task. We
also report mean cost C(h) and latency L(h). For H ARNESS P RO, all metrics are given as mean ±
sample standard deviation over three runs on Terminal-Bench 2 and SWE-Bench Pro, and two on
ProgramBench. The token prices used to calculate cost are listed in Table 4 in the appendix.

5.2   M AIN R ESULTS

Table 2 compares H ARNESS P RO with several baseline methods across three benchmarks. With
GPT-5.5 and Codex, RHO improves performance over Vanilla on all three benchmarks, but also
increases execution cost. On SWE-Bench Pro, for example, its mean cost per task rises by 42.6%,
from $1.88 to $2.68. In contrast, the heavy mode of H ARNESS P RO achieves the highest pass rate
across all three benchmarks at lower cost than RHO. On Terminal-Bench 2, the heavy mode of
H ARNESS P RO reaches a mean pass rate of 80.8% across three runs, 4.5 percentage points above
RHO, with 33.9% lower mean cost. The advantage extends to ProgramBench, where its 69.6% pass
rate exceeds RHO’s 68.8% at 17.8% lower mean cost ($2.95 vs. $3.59). These results show that
better task performance need not come at a higher execution cost. For the medium mode, we retain
strong task performance while reducing cost further. On SWE-Bench Pro, it achieves a 79.0% pass
rate compared with RHO’s 80.0%, while reducing the average cost per task by 53.0%, from $2.68
to $1.26. The lite mode lowers cost further, outperforming Vanilla on all three benchmarks while
spending 17.7–57.4% less, making it an economical choice for deployment under strict budget
constraints. Even with comparable iteration budgets, H ARNESS P RO achieves a better performance–
cost trade-off than RHO+Iteration. Our medium mode matches the performance of RHO+Iteration
on Terminal-Bench 2 at 31.7% lower cost. Moreover, on ProgramBench, our heavy mode raises
pass rate by 1.3 percentage points while lowering mean cost by 5.8%.
The results with GLM-5.2 and Claude Code follow a similar pattern: the heavy mode of H AR -
NESS P RO surpasses RHO on all three benchmarks at lower cost, while the medium and lite modes
outperform Vanilla in pass rate, often at substantially lower cost. Moreover, although latency is
not an objective, cost optimization yields faster task completion in most cases. For example, on
SWE-Bench Pro, our heavy mode reduces mean latency from RHO’s 520 to 412 seconds.

5.3   A NALYSIS OF E VOLVED H ARNESSES

To understand how H ARNESS P RO improves the performance-cost trade-off, we inspect its evolved
harnesses. On Terminal-Bench 2 and SWE-Bench Pro, they select an execution profile from each
task description. Each profile specifies a reasoning effort level and a tool-call budget. The lite,
medium, and heavy modes use different rubrics for profile selection. Runtime hooks enforce the
selected budget. For example, on Terminal-Bench 2, when H ARNESS P RO-Medium selects the stan-
dard profile, the hooks remind the agent to produce parallel tool calls and avoid redundant checks
after 14 tool calls, focus on completing and verifying the task after 26, and block further calls after
44. The reminders are appended to tool results, preserving the prompt prefix for cache reuse. Along-
side these dynamic mechanisms, the evolved harnesses also reduce static context redundancy. On
Terminal-Bench 2, for instance, tool-output compression like RTK (Szymkowiak, 2026) folds re-
peated logs and condenses long outputs, while streamlined developer instructions reduce redundant
input. This combination curbs recurring prompt overhead and limits the context growth caused by
verbose tool feedback, thereby reducing execution cost and latency. Implementation details of these
harnesses are in Appendix D.1.

5.4   E VOLUTION DYNAMICS

Figure 4 tracks test-set performance and cost across epochs. Across all three benchmarks,
H ARNESS P RO advances the performance-cost Pareto frontier through recursive harness self-
improvement. On Terminal-Bench 2, each round of evolution improves the retained Pareto frontier,
yielding higher pass rates at lower costs. For example, the pass rate of the heavy mode rises from
74.6% in epoch 1 to a mean of 80.8% in epoch 3, while mean cost per task falls from $0.91 to
$0.72. The lite and medium modes also maintain their pass rates from epoch 2 to 3, while their
mean costs fall from $0.61 to $0.43 and from $0.68 to $0.56, respectively. The benefits of additional
evolution epochs are particularly clear on SWE-Bench Pro, where a single run may raise pass rate
at the expense of higher cost. In the medium mode, pass rate rises from 70.0% in epoch 1 to 77.0%
in epoch 2, but mean cost also rises from $1.57 to $1.66. Only in epoch 3 does it improve both
metrics, with pass rate rising to 79.0% and mean cost falling to $1.26 per task. On ProgramBench,
the fourth epoch likewise lowers costs across all three modes while maintaining similar pass rates.
These patterns highlight an advantage of recursive self-improvement over single-round evolution.

 6                     C ONCLUSION

We introduced H ARNESS P RO, a label-free approach to recursive harness self-improvement that im-
proves task performance while reducing execution cost. To this end, it coordinates trajectory diagno-
sis and harness modification through a multi-agent framework, with a dedicated planner proposing
update plans and LLM-generated tests guiding candidate evaluation. Rather than producing a single
harness, H ARNESS P RO offers cost-focused (lite), balanced (medium), and performance-focused
(heavy) alternatives to meet different deployment budgets. Experiments across three benchmarks
show that H ARNESS P RO can improve task performance while reducing execution cost, with addi-
tional benefits in latency. Further analysis attributes these gains to the synergy of multiple evolved
mechanisms and shows sustained progress through recursive self-improvement. These findings show
that performance and efficiency can improve together, making cost-aware evolution a promising di-
rection for practical recursive self-improvement in harness optimization.

      deduped: list[str] = []
      index = 0
      while index < len(lines):

  def compact text(text: str, ∗, head chars: int, tail chars: int) −> str:
      lines = text.splitlines()
      deduped: list[str] = []
      index = 0
      while index < len(lines):
          next index = index + 1
          while next index < len(lines) and lines[next index] == lines[index]:
              next index += 1
          repeats = next index − index
          deduped.append(lines[index])
          if repeats > 2:
              deduped.append(f"[previous line repeated {repeats − 1} more times]")
          elif repeats == 2:
              deduped.append(lines[index])
          index = next index
      compact = "\n".join(deduped)
      if len(compact) <= head chars + tail chars:
          return compact
      omitted = len(compact) − head chars − tail chars
      return (
          compact[:head chars]
          + f"\n... [{omitted} characters omitted; use the raw path for a targeted range]
  ...\n"
          + compact[−tail chars:]
      )

  # ProgramBench Reconstruction Harness

  Use this harness as a task−agnostic control loop for rebuilding a program from
  documentation and black−box observations. It supplements the benchmark rules;
  it never permits source retrieval, internet access, decompilation, tracing, or
  reuse of the reference executable.

  ## Evidence−first workflow

  1. Read all bundled documentation and turn it into a compact behavior ledger:
     commands, flags, inputs, outputs, exit status, file effects, defaults, error
     behavior, formatting, and explicitly documented edge cases.
  2. Establish a runnable skeleton early. Create ‘compile.sh’, build a minimal
     independent executable, and confirm the complete build/run cycle before
     investing in secondary behavior.
  3. Probe the reference through its normal public interface. Use small,
     discriminating experiments that separate plausible behaviors; record the
     observed input, output, status, and state change instead of relying on
     assumptions based on the program name.
  4. Prioritize breadth before polish. Implement the documented happy paths and
     common input classes, then error handling, boundary cases, formatting, and
     low−frequency options. Keep a list of remaining unsupported behavior.
  5. Compare your implementation and the reference on the same locally generated
     cases. When they differ, reduce the case and fix the underlying general rule
     rather than adding a one−off special case.
  6. Rebuild from a clean state periodically. A solution that works only because
     of cached artifacts, undeclared tools, or files outside the submission is
     not complete.
  7. Before finalizing, verify that ‘compile.sh’ is executable, produces
     ‘./executable’ without network access, and that representative success and
     failure probes agree with the reference.

  ## Efficiency rules

  − Batch independent documentation reads and related probes when practical.
  − Prefer high−information probes over broad random exploration.
  − Keep outputs bounded and summarize findings in the behavior ledger.
  − Stop repeating probes once a stable rule has been established.
  − Reserve the final portion of the budget for a clean rebuild and end−to−end
    validation rather than continued exploration.

  ## Reference lifecycle

  Keep the black−box reference available until differential validation is finished.
  Develop a separately built candidate at another path, with the same executable
  basename where relevant. Do not overwrite the reference during implementation.
  If a permitted move is necessary, retain the execute−only reference on the same
  filesystem without reading/copying its bytes or changing its permissions.
  The reference is only a development oracle: never include it in the submission
  or invoke it from the submitted implementation. Self−authored expected outputs
