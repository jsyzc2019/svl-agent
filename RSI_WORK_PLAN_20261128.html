二、六篇论文指向同一个结论——这不是巧合

把 9 篇全文横向叠在一起，最刺眼的不是"agent 越来越会改自己"，而是它们从六个独立方向撞上了同一堵墙：改动的"可信度"比改动本身更难。
论文它证明的那一面
Meta-Harness好的改进来自原始诊断经验（代码/轨迹/失败），不是分数摘要——信息不能被压扁
Winner's Curse小样本上"更好"是幻觉（高估 13–20 分），必须留出集 + 标准误
HDA即便有留出集，增益也可能来自过拟合/测试算力——要拆解归因
Who Verifies验证器自己会塌（always-pass）且下游分数看不出来——锚点 + 外部裁判
Trusting Trust改进的数据来源本身可被投毒，污染会跨代遗传——质疑每个自改进数据源
Singularity-Bench连评测框架都能被 agent 利用（9/10 OWASP 类）——验证器需要防御工事

这正好与综述的三大挑战一一对应：Reliable verification / Safe inheritance / Autonomy attribution。也就是说，学界已把这堵墙命名为 RSI 的核心未解问题——而本仓从第一天起的纪律（预注册 SHA 先于取证、逐字锚点、判定权归用户、不伪造日志）恰好全落在这堵墙上。

四、工作计划 · 分优先级（每项含验收标准与判定权）

以下全部是建议，不是执行。凡涉及内核/权威态/判定规则的改动，一律先预注册、再由用户裁定；本计划自身不改任何文件。

P0补上挂着的验证器洞 —— 但按纪律，先由你定调

事项：verify_external.py:156 的 if cid not in jd: continue 会静默跳过缺失样本的判定。静态审计与 §4S17 都指出这是"验证器自己有洞"，当时的裁决是存档不动手。现在论文证据已经把它从"隐患"升级为"教科案例"——Who Verifies 证明塌掉的验证器下游分数看不出来，Trusting Trust 证明数据源可被投毒。

建议动作（须你批准后执行）：改成严格相等校验——样本集 id 与判定集 id 必须完全相等，缺失或多余都 hard-fail，并写一条负向自咬测试（故意删一个判定，验证器必须拦下）。改动局限在验收器，不碰 verdict/l3/权威哈希。

验收：① 当前真实投递包 16=16 仍 PASS；② 人为删一条判定 → FAIL；③ 权威态仍 CONSISTENT、0f3ccb13/fe56291b 未动。判定权：你。这是本计划里唯一我建议优先动的实现项，但你的归档裁决仍优先。

P1建立"改前 vs 改后"留出集对打机制

事项：本仓至今没有"同一留出集上让起始版与当前版对打"的机制——而这正是 Winner's Curse（128 次评估把 RMSE 15.5→5.7）、HDA（拆解过拟合/算力）、综述 L5 第二层硬要求共同指向的缺口。

建议动作：设一套只用于评测的冻结留出集（与现有 samples 物理隔离、带独立哈希），每次内核/验收器改动前后各打一次分，连同标准误一起记进交接文档。第一版只做"记录"，不改判定规则。

验收：留出集哈希入预注册；至少一次真实改动留下前后对照数字；报告里出现"增益 ± 标准误"而非裸分。判定权：留出集构造与阈值由你定。

P1给改进机制加"增益归因"一栏

事项：HDA 证明 harness 演进的增益 54% 来自过拟合、14% 来自算力；Harness Ceiling 要求按失败成分决定改哪一层。本仓的 REORIENT 补丁等改动目前只记"做了什么"，没记"增益可能来自哪"。

建议动作：在既有日志结构里加一个可选字段 gain_attribution（如 {overfit_risk, compute_change, residual}），随每次 evolve 落账；先手写两三条真实改动的归因作为样例，不自动化。

验收：≥3 条改动带归因字段；不改内核判定逻辑；权威态无漂移。判定权：字段设计由你定。

P2把"错题本/负面结果"从散落文档收敛成结构化账本

事项：No Second Run 把"账本"当贡献而非模型；Winner's Curse 要求报标准误。本仓 §4S 全程留档很全，但"哪次改失败、为什么"是散文式的。

建议动作：新增一个轻量的 negative_results.jsonl（失败尝试 + 原因 + 归因 + 日期），与既有心跳账本并列；把静态审计 6 条、编号错配 3 次、GHA 调度丢拍等已知负面结果先补录进去。

验收：文件可读、≥5 条历史负面结果入账、不触碰权威态。判定权：你（是否值得单独建文件）。

P2对照 Exo / Hyperagents 的三条架构，做一份"差距清单"而非模仿

事项：Exo 的 append-only 历史 + guardian、Hyperagents 的"外层父代选择/评估协议固定"、Spotify 的改动人工审核——三条都和本仓同构，但都不该照搬。

建议动作：整理成一页"本仓已具备 / 可选借鉴 / 明确不采纳"三栏清单，每栏给出理由。尤其写清：本仓的"判定权归用户"比 Exo 的 build-success guardian 和 Hyperagents 的固定外层都更严，是刻意选择，不是落后。

验收：一页 HTML/表格，零代码改动。判定权：你。

P2把论文纠错方法论固化为一条检查项

事项：三轮检索中，用户提供的编号错配率 100%（5/5），公众号清单 13 引用错 10。这不是偶然，是"标签≠事实"的系统性风险。

建议动作：在今后任何"外部论文/审计引用"流程里加一步强制回源（arXiv abs 页核对标题+作者+日期），并把已核实的 12 篇正确编号表固化到交接文档附录，避免重复劳动。

验收：编号对照表入 §4S 附录；下次引用先查表。判定权：流程建议，你定是否立为纪律。

一句话总览：论文给出的不是"快去升级"的压力，而是一面镜子——本仓最稀缺的从来不是新机制，而是把"改动是否真的更好"证明得足够干净。P0 补验证器洞、P1 建留出集对打与增益归因，正是把这面镜子擦亮；P2 都是可选沉淀。全计划零强制项，等你逐条裁决。
