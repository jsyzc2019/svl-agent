二、核心思想：把优化循环折叠进任务执行

传统做法（Meta-Harness、GEPA、AlphaEvolve）是外部优化循环：先备好 benchmark，候选 harness 跑几百道题，按得分回头改代码。Exo 指出这在真实生产里三处卡壳：75% 团队无评测集长任务单次跑数天/数周harness 在执行中固定不变。它的解法是把优化器搬进正在运行的 agent 内部。

"Harnesses have two special properties that allow us to bring the optimizer into the core policy itself. First, a harness revision can be realized in the same action domain as ordinary task work, which we refer to as optimizer symmetry... Second, the harness is operationally homoiconic: its policy is code, and that code is represented as files the agent can observe and manipulate with its code-editing tools."

两条性质：优化器对称性（改 harness 和做任务用同一套动作：看源码、改文件、跑测试、请求激活）+ 操作上是同构的（策略即代码、代码即 agent 能读写的文件）。于是"何时改、怎么改"这套改进策略本身也成了可编辑对象——每一代 successor 都能用新的改进策略，且仍能继续改自己，不依赖模型重训。

三、两个失败模式与两条契约

让 agent 边跑边改自己，论文点出两个致命失败模式，这是整篇最硬的部分：

失败模式原文后果
Fate-sharing（命运共享）"a faulty edit can disable both the agent and the logic it would use to diagnose and repair itself"一次坏改动同时废掉 agent 和它用来诊断修复自己的那套逻辑
Unprotected state（无保护状态）"edits to unprotected state can erase accumulated progress and execution evidence, including records of failed revisions"改动抹掉累计进展与执行证据，连"哪些改失败过"的记录都没了

对应两条形式化契约（原文明写）：

Storage contract: "The storage contract requires this history to be append-only: H(dt) ⪯ H(dt+1)... Existing records cannot be overwritten or deleted. Memory and task artifacts may have mutable current values, but updates must retain prior versions for recovery."
Replacement contract: "Activating this as the active policy must therefore require a check that lies outside of the policy itself. We call this mechanism the guardian G(st, π′)... πt+1 = π′ if G=1, else πt."
这两条契约的诚实边界（论文自己写）："this protection holds regardless of how the agent chooses its edits, but does not on its own guarantee improved behavior or continued progress." ——保护的是"改不坏、赖不掉账"，不保证越改越好。这一句，和咱们项目"哈希能证一致、不证判据有效"是同一件事的两种说法。

四、架构：kernel / userspace 式的两层切分

借 Exokernel 思想（"expose it at the lowest level of abstraction to maximize the space of behaviors that can be expressed above it"），把 harness 切成两层：

受保护机制层（kernel 类比）可编辑策略层 executor（userspace 类比）
规范化执行历史（append-only、带 cost/token 注解、可查询）工具实现与选择、上下文组装与压缩、prompting、记忆/技能索引检索
带版本的 artifact store（记忆、技能、沙箱快照）外部集成：服务适配器、任务调度
凭证存储、沙箱 API、独立的 guardian（控制权在策略之外）以及"何时/如何发起进一步自我改进"的那套程序本身

关键操作顺序：① 把 executor 源码挂载进沙箱，agent 用现成工具就能看改；② 通过一个受保护工具请求替换，guardian 构建候选、通过检查才激活。替换请求与结果都记进事件历史。独立回滚：executor 策略、durable 状态、环境沙箱三者可分别回滚，且回滚保留原始执行记录——"allowing the agent to retain evidence of what it tried even after a rollback"，失败尝试的证据留给未来决策。

六、诚实的局限（论文附录原文，含金量最高）

"Guardian acceptance establishes only the properties actually checked: build success alone guarantees neither task correctness nor improvement. ... Preservation alone does not ensure liveness."
"Snapshot scope depends on the provider: Docker image snapshots omit process memory and host-mounted source. Neither reverses external effects, which require domain-specific recovery."
"The storage and replacement mechanisms must remain outside the executor's editing authority. Direct storage access or unrestricted administrative deletion would invalidate complete mediation; the broadly writable development configuration does not enforce these restrictions."
翻译成人话：
① 默认 guardian 只验"能不能编译"，不保证任务正确、更不保证变强；更强的 guardian（LLM 当裁判、在 fork 环境里试跑）要花更多成本，怎么按改动后果匹配验证强度是开放问题。
② 快照回卷不能撤销已经发生的外部副作用（发出去的消息、已调用的 API），这跟咱们之前静态审计里"rebase || true 吞失败"是亲缘问题。
③ 保护成立的前提是机制层在 agent 编辑权限之外；但宽松可写的开发配置本身并不强制这个隔离——纸面契约 ≠ 实现强制。作者在 LinkedIn 讨论里也有同行追问"沙箱回卷 ≠ 外部效果回卷"，正是这一点。
