一、文章核心：把交付线逐站交给 agent

Write→Pass CI→Review→Approve→QA→Fix breaks→Run the line→

核心叙事：AI 让写代码变快，review 成了瓶颈。Runway 没有要求 agent 写出更好的 change，而是逐站把软件交付的每个环节交给 agent——每交一站，先定"如何判断这次交接"，再看结果。瓶颈随之后移到下一站：write→CI→review→approve→QA→fix breaks→run the line。最终工程师的角色从"读 diff"转为"决定造什么、修 agent 卡住的地方、守住度量诚实"。

最关键的工程机制（安全护栏，全部由真实事故倒逼）：
  • L264 read-only shadow：否则read-only发现的bug会上线并重跑已完成工作
  • L267 gates re-check at exact commit：否则PR被override合并、reviewer签字后agent继续push
  • L270 external actions idempotent：否则agent争抢同任务互相取消
  • L273 people by policy not accident：否则旧merge工具3次卡在prompt等人、阻塞超1小时
  • L276 rollback in one call：否则release train因噪声信号撤掉所有生产池
与本仓框架高度同构：shadow mode（先读后写）≈ 预注册门禁；gates re-check at exact commit ≈ 预注册 SHA256 锁存 + 验证对象=最终对象；friction map ≈ 判据自审/审计工具本身；"在看结果前先定判据"≈ 本仓防后知纪律。但同构 ≠ 独立验证——这是两个不同来源各自收敛到相似做法，不能互相当作证据。

七、复述 vs 长牙：本框架该吸收什么

编译成门禁（长牙）

  1. 风险分级批准：按风险+关键路径分流，未分级即 flag——防"一律自动/一律人工"的粗暴做法
  2. shadow mode 先读后写：新判据上线前必须 read-only 跑一段、人逐条判定——本仓"预注册"纪律的更具体形态
  3. gates re-check at exact commit：验证对象必须=最终合并对象，签字后 push 则失效——直击"验证后漂移"，可编译成哈希门禁
  4. friction map 同规模归一化：按同类 PR 规模归一化找返工热点，不凭绝对数——审计定位的严谨方法
  5. 外部动作幂等：agent 并发争抢同任务要幂等——防重复执行副作用

只记观察

38%/3000 PR 月增等规模数字——本框架不产 PR，不适用，不造模块。

克制：与上一轮一致，本次仍不强造通用模块。"gates re-check at exact commit"与已有预注册 SHA256 锁存高度重叠，标记为其强化而非新模块；shadow mode/风险分级属方法论层，先入库为 reasoning_lesson 观察复现。
